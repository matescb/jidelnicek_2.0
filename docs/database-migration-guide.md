# Database Migration Guide

## Overview

This project uses Alembic for database schema management. All application tables, functions, and triggers are managed through migrations, not Docker init scripts.

## Architecture

### Docker PostgreSQL Init (`docker/postgres/00_init_minimal.sql`)
Only handles infrastructure setup:
- PostgreSQL extensions (uuid-ossp, pg_trgm, etc.)
- Database configuration (timezone, timeouts)
- User creation and permissions
- NO application tables

### Alembic Migrations (`migrations/`)
Manages all application schema:
- All tables (auth_*, recipe_*, trip_*, etc.)
- Indexes and constraints
- Functions and triggers
- Schema updates over time

### Application Startup (`docker/entrypoint.sh`)
1. Waits for database to be ready
2. Runs Alembic migrations
3. Seeds initial data if needed
4. Starts the application

## Development Workflow

### Fresh Start
```bash
# Reset database to clean state
./scripts/reset-db.sh

# Start services (will run migrations automatically)
docker-compose up
```

### Create New Migration
```bash
# Generate migration from model changes
docker-compose run --rm app alembic revision --autogenerate -m "Add new feature"

# Or create empty migration
docker-compose run --rm app alembic revision -m "Custom migration"
```

### Apply Migrations
```bash
# Migrations run automatically on startup, but you can run manually:
docker-compose run --rm app alembic upgrade head
```

### Rollback Migration
```bash
# Rollback one migration
docker-compose run --rm app alembic downgrade -1

# Rollback to specific revision
docker-compose run --rm app alembic downgrade <revision>
```

## Production Deployment

1. Build container with latest code
2. Run migrations before deploying new version:
   ```bash
   alembic upgrade head
   ```
3. Deploy new containers
4. Migrations are idempotent - safe to run multiple times

## Troubleshooting

### "Table already exists" errors
- Database has tables from old Docker init scripts
- Solution: Run `./scripts/reset-db.sh` to start fresh

### Migration fails
- Check migration file for errors
- Ensure models match migration
- Check for dependency issues

### Seed data issues
- Seed script runs after migrations
- Check logs for specific errors
- Ensure categories/tags tables exist

## Best Practices

1. **Never modify migrations after deployment**
   - Create new migrations for changes
   
2. **Test migrations locally first**
   - Run upgrade/downgrade cycle
   - Verify data integrity

3. **Keep migrations focused**
   - One logical change per migration
   - Clear, descriptive names

4. **Review autogenerated migrations**
   - Alembic may miss some changes
   - Add custom SQL if needed
