### Implication for this audit

A line-level WCAG 2.2 audit against TSX is **not possible** today. This report therefore does three things:

1. Documents the most severe a11y issue: **a documented WCAG 2.1 AA acceptance criterion (Component Library §5, PRD) with no implementation to verify it against** — i.e., the gate exists on paper only.
2. Catalogues **HTML/config-level issues that already exist** (`index.html`, `tailwind.config.js`, design tokens in `jidelnicek_Component Library.md`).
3. Produces a **forward-looking WCAG 2.2 AA implementation contract** keyed to the planned components and the 5 critical user flows below, so the team can build against it rather than retro-fitting later.

## TL;DR — top 5 a11y issues

1. **`frontend/index.html:2` — `lang="en"` on a Czech application.** This is the single highest-impact, lowest-effort fix in the entire codebase. Screen readers will use English phonetics for Czech text, making the app unintelligible to blind cs-CZ users. **WCAG 3.1.1 (A).** Fix: `lang="cs"`.
2. **No source code → no enforcement of the WCAG promise.** `Documentation/jidelnicek_Component Library.md:553-559` commits to "WCAG 2.1 AA compliance … keyboard navigation … focus indicators visible and clear … screen reader tested." There is nothing to test, no axe-core, no jsx-a11y, no Playwright a11y snapshots wired into `frontend/package.json`. Compliance is currently aspirational only.
3. **Brand color (`--color-primary-600: #2D5016` on white) is fine, but the `--color-primary-500: #567f2d` placeholder used as the secondary CTA in the spec will fail 4.5:1 contrast when used for text on white.** And the lighter shades (`-100` to `-400`) are explicitly defined and *will* be used for text per the spec, with no contrast guardrails. **WCAG 1.4.3, 1.4.11 (AA).**
4. **Drag-and-drop day cards (`Component Library` §3.3, US §218/§263) ship with `@hello-pangea/dnd` — which does NOT natively meet WCAG 2.2 SC 2.5.7 (Dragging Movements).** The spec mentions "Keyboard alternative (Ctrl+arrows)" but provides no single-pointer alternative for users who cannot drag (e.g., switch users, voice-control users on iOS Switch Control). A "Move to…" menu must be added. **WCAG 2.5.7 (AA, new in 2.2), 2.1.1 (A).**
5. **Touch target spec is inconsistent.** Component Library §2.1 promises 44×44 px (good), but §2.2 specifies inputs at height **32px (Small)** and §2.5 confirmation dialog buttons have no min size. WCAG 2.2 SC **2.5.8 Target Size (Minimum)** requires **24×24 CSS px** for *every* pointer target with spacing exceptions. The Small button at 32×(unknown width) and inline icon controls on cards (Edit/Delete/Notes on the Meal Card, ⭐ rating stars on the Recipe Card) are at risk.

## Findings

> Format: `path:line — WCAG SC — what / why / fix / effort`
> *Effort key:* XS = <30 min, S = <2 h, M = half-day, L = >1 day, XL = >1 week.

### CRITICAL (blocking AT users)

**A-C-01 — `frontend/index.html:2` — SC 3.1.1 Language of Page (Level A)**
- *What:* `<html lang="en">` on a Czech-language product (title is `Jídelníček - Meal Planning Made Easy`, copy throughout `Documentation/jidelnicek_US.md` is in Czech context).
- *Why:* Screen readers (NVDA, JAWS, VoiceOver, TalkBack) switch pronunciation engines on `lang`. With `en`, Czech words like "Jídelníček", "polévka", "obědy" are read with English phonetics — completely unintelligible. Also breaks hyphenation, language-aware spellcheck, and Google Translate offers.
- *Fix:* `<html lang="cs">`. If the app supports language switching via i18next (it does — `i18next-browser-languagedetector` is installed), the root component must call `document.documentElement.lang = i18n.language` on every `languageChanged` event. Also set `<html dir>` accordingly; given the Component Library §5 mentions "RTL layout support ready", wire `dir="ltr"` / `dir="rtl"` from i18n too.
- *Effort:* XS (one line in `index.html`) + S (one effect in `App.tsx`/`i18n.ts` once code is written).

**A-C-02 — Whole codebase — SC 4.1.2 Name, Role, Value (Level A) [Conformance Gate]**
- *What:* No source files exist. The Component Library spec promises ARIA labels, focus management, screen-reader-tested behavior — but nothing has been built, nothing has been tested, nothing prevents the first PR from shipping inaccessible markup.
- *Why:* WCAG conformance is a property of *delivered* code, not of plans. Without enforcement infrastructure (lint, CI a11y tests), the documented commitments will silently rot.
- *Fix:* Before ANY component is implemented, install and enforce in CI:
  - `eslint-plugin-jsx-a11y` with `recommended` config in `frontend/.eslintrc.js`.
  - `@axe-core/react` in dev mode (logs violations to console during development).
  - `jest-axe` / `vitest-axe` for component-level tests (every component must have `expect(await axe(container)).toHaveNoViolations()`).
  - `@axe-core/playwright` for E2E smoke on each critical flow.
  - Add a "a11y" CI job that fails the build on any axe violation tagged `wcag2a`, `wcag2aa`, or `wcag22aa`.
- *Effort:* M (config + first wiring), then ongoing per component.

**A-C-03 — `frontend/index.html` — SC 2.4.1 Bypass Blocks (Level A)**
- *What:* No `<main id="main">` landmark and no `<a href="#main" class="skip-link">` skip link present in the shipped HTML shell. The shell renders an empty `<div id="root">` only.
- *Why:* Keyboard users must currently tab through the entire global header on every page. The Component Library §2.4 shows a sticky header with logo, 4 nav items, profile, and lang switch — at least 8 tab stops before reaching content.
- *Fix:* In the layout component (when written), render a visually-hidden-until-focus skip link as the first focusable element, plus `<header role="banner">`, `<nav aria-label="Hlavní navigace">`, `<main id="main" tabindex="-1">`, `<footer role="contentinfo">`. The `main` must receive focus on route change (set `mainRef.current?.focus()` in `useEffect([location.pathname])`).
- *Effort:* S.

**A-C-04 — Component Library §3.3 (Drag-and-Drop Day Cards) — SC 2.5.7 Dragging Movements (Level AA, NEW in 2.2)**
- *What:* The spec relies on `@hello-pangea/dnd` (per `package.json`). This library does ship keyboard support (space + arrows), but SC 2.5.7 also requires a **single-pointer alternative** — a way to reorder *without* a continuous drag gesture. The spec mentions "Keyboard alternative (Ctrl+arrows)" but says nothing about pointer-only users (e.g., users with tremor, head-pointer users, or anyone using iOS Switch Control / Voice Control "tap" gestures who cannot perform a sustained drag).
- *Why:* SC 2.5.7 is non-negotiable at AA in 2.2. Drag-only reordering is a documented failure pattern.
- *Fix:* On every draggable card, expose a "More" menu (3-dot button) with at least: **Move up**, **Move down**, **Move to day…** (combobox of all days). The menu items must perform the same state mutation the drag operation performs. Document this in the component spec.
- *Effort:* M per draggable surface (day cards, meal-within-day reorder, ingredient reorder in recipe editor — at least 3 surfaces from US §218/§263/§202).

**A-C-05 — Critical-flow forms (login, register, recipe create, trip create, participant editor) — SC 1.3.1 / 3.3.1 / 3.3.2 / 4.1.2 (Level A) + SC 3.3.7 Redundant Entry (Level A, NEW in 2.2) + SC 3.3.8 Accessible Authentication Minimum (Level AA, NEW in 2.2)**
- *What:* The Component Library §2.2 shows form inputs but provides **no contract** for: (a) `<label>` association (just "helper text 12px below"), (b) `aria-invalid` / `aria-describedby` wiring on error, (c) `aria-required`, (d) error summary at top of form, (e) password autocomplete tokens, (f) prevention of CAPTCHA/cognitive function tests on login (SC 3.3.8).
- *Why:* Forms are the #1 a11y failure surface in production apps. Without an explicit contract, react-hook-form (which is in `package.json`) will be used in many incompatible patterns.
- *Fix:* Adopt a `FormField` primitive that *enforces*:
  ```tsx
  // pseudocode contract — every form field MUST render through this
  <FormField name="email" label="E-mail" required>
    {(field) => <Input
      type="email"
      autoComplete="email"        // SC 1.3.5
      aria-invalid={!!field.error}
      aria-describedby={cn(field.helperTextId, field.errorId)}
      aria-required={field.required}
      {...field.props}
    />}
  </FormField>
  ```
  - For registration, ensure `autoComplete="new-password"` and for login `autoComplete="current-password"` (SC 3.3.8 — never block paste, never block password managers).
  - For trip creation step 2 onwards, never re-ask for trip name, dates, or participant info already entered (SC 3.3.7 Redundant Entry). Pre-fill or display read-only.
  - Submit must focus the first invalid field on validation failure, and announce an error summary via `role="alert"` or `aria-live="assertive"`.
- *Effort:* L (one-time primitive), then XS per form.

### HIGH (significant barriers)

**A-H-01 — `Documentation/jidelnicek_Component Library.md:8-90` — SC 1.4.3 Contrast (Minimum) and SC 1.4.11 Non-text Contrast (Level AA)**
- *What:* The palette includes light shades (`primary-100..400`, `error-100..400`, etc.) intended to be used as text and as UI component borders, with no contrast matrix documented.
  - `--color-warning-500: #f59e0b` on white = 2.13:1 (fails 4.5:1 normal text, fails 3:1 non-text).
  - `--color-error-400: #f87171` on white = 2.71:1 (fails).
  - `--color-success-500: #22c997` on white = 2.13:1 (fails).
  - `--color-primary-500: #567f2d` on white = 4.34:1 (fails normal-text 4.5:1, passes large-text 3:1).
  - `--color-primary-600: #2D5016` on white = **9.04:1** — safe.
  - `--color-secondary-500: #9f6e42` on white = 3.62:1 — passes large-text only.
- *Why:* Without a documented contrast contract, designers will reach for the 400/500 shades for body text and form borders, silently failing AA.
- *Fix:* In the Component Library, add a **"Text contrast" subsection** that explicitly states, for each token: "approved for body text" / "approved for large text only" / "approved for non-text UI only" / "decorative only". Provide a Tailwind plugin or stylelint rule that flags `text-warning-500`, `text-error-400`, `text-success-500`, `text-secondary-500` in `.tsx` source.
- *Effort:* S (contrast table) + S (lint rule).

**A-H-02 — Component Library §2.1 vs §2.2 vs §2.5 — SC 2.5.8 Target Size (Minimum) (Level AA, NEW in 2.2)**
- *What:* Buttons claim 44×44 min (good), but Small button is 32 px high (§2.1 Sizes), Text Input is 40 px high (§2.2), and the Recipe Card icon row (⭐ rating, 👤 author chip, ✏️ Edit/🗑️ Delete/📝 Notes on Meal Card §2.3) is unspecified.
- *Why:* SC 2.5.8 requires **24×24 CSS px** for every target (with spacing exceptions). The Small button at 32 px height passes — but its *width* is `padding 8px 12px + content`, which may yield <24 px wide for icon-only smalls. Inline rating stars and inline meal actions almost certainly fail.
- *Fix:* Add to the Component Library a hard rule: "All interactive targets, including icon-only buttons, rating stars, checkbox affordances, and inline card actions, must have a hit area of **≥ 44×44 CSS px on mobile** and **≥ 24×24 CSS px on desktop with ≥ 24 px center-to-center spacing**. Where visual size is smaller (e.g., 16px star icons), use a transparent padding box to extend the hit area." Provide a `<TouchTarget>` utility wrapper.
- *Effort:* S (spec) + M (wrapper + retrofit during impl).

**A-H-03 — Component Library §2.5 (Modals) — SC 2.4.3 Focus Order, SC 2.1.2 No Keyboard Trap, SC 2.4.11 Focus Not Obscured (Level AA, NEW in 2.2)**
- *What:* Modal contract states "Focus trap enabled, ESC key to close" — good, but does not specify: (a) where focus lands on open (must be first focusable element OR the dialog's `<h2>`), (b) where focus returns on close (must be the trigger element), (c) that the focus indicator must remain visible and **not be obscured** by sticky headers/footers (SC 2.4.11, new in 2.2).
- *Why:* Radix Dialog (in use per `package.json`) handles trap + ESC + initial focus + return focus *correctly out of the box* — but only if `<Dialog.Trigger>` and `<Dialog.Content>` are used and not bypassed. The spec invites custom implementations.
- *Fix:* Mandate Radix Dialog as the *only* approved modal primitive in the Component Library. Forbid custom modals. Document that the focus trap is provided by Radix and must not be overridden. Add an ESLint rule (`no-restricted-imports` for `@mui/material/Dialog`, `@headlessui/react/Dialog` if the team wants to standardize — currently both are in `package.json`, creating three competing modal stacks: Radix, MUI, Headless UI).
- *Effort:* S (decision + lint rule).

**A-H-04 — Three competing UI libraries in `frontend/package.json` — SC 3.2.4 Consistent Identification (Level AA)**
- *What:* `package.json` includes `@mui/material@^7.2.0`, `@radix-ui/react-*` (10+ primitives), and `@headlessui/react@^1.7.17`. Each has different a11y characteristics:
  - Radix: best-in-class a11y, headless.
  - MUI v7: good a11y but uses Emotion, can clash with Tailwind.
  - Headless UI: good but lower coverage than Radix.
- *Why:* Same-purpose components (e.g., a Select) implemented by different libs will have different screen-reader announcements, different focus models, and different keyboard shortcuts — breaking SC 3.2.4 (Consistent Identification).
- *Fix:* Pick **one** primitive layer (recommendation: Radix UI + Tailwind, since most Radix primitives are already installed). Remove the other two. Document in an ADR.
- *Effort:* M (decision + cleanup before code is written; XL if deferred).

**A-H-05 — Component Library §3.6 Empty States, §3.7 Error States, §3.2 Confidence Indicator — SC 1.4.1 Use of Color (Level A) + SC 1.3.3 Sensory Characteristics**
- *What:* Confidence indicators rely on emoji + color only: ✅ green / ⚠️ yellow / ❌ red. No text-equivalent role label. Same for "Accuracy: 99.9% guaranteed" with ⚠️ icon (§3.8).
- *Why:* Color-blind users (8% of men) and screen-reader users with images/emoji off will lose the severity signal. Many emoji are announced inconsistently across NVDA/JAWS/VoiceOver/TalkBack.
- *Fix:* Pair every status icon with a **text label** ("Vysoká přesnost", "Střední", "Nízká") and an `aria-label` on the icon container. For emoji icons, use a real `<svg role="img" aria-label="…">` or wrap with `<span aria-hidden="true">⚠️</span><span class="sr-only">Upozornění:</span>`.
- *Effort:* S per indicator.

**A-H-06 — `Component Library §2.3` Recipe Card — SC 2.4.4 Link Purpose (In Context) + SC 1.1.1 Non-text Content (Level A)**
- *What:* Recipe Card spec says "Click area: Entire card" and shows `[Image]` plus rating, time, kcal, tags — but no contract for: (a) the card's accessible name (must include recipe name, not just "Recipe Card"), (b) image `alt` (must describe the dish or be empty if decorative + name is in adjacent text), (c) how nested action buttons (Edit/Delete/Notes from Meal Card §2.3) avoid nested-interactive antipattern when the whole card is clickable.
- *Why:* The "entire card clickable" + "internal action buttons" pattern is the most common a11y antipattern in card UIs. It produces nested `<button>` inside `<a>` (invalid HTML), or screen-reader users hear "button button button" without knowing what the *card* is.
- *Fix:* Use the "card as block with a single primary link" pattern:
  ```tsx
  <article aria-labelledby={`recipe-${id}-title`}>
    <img src={…} alt="" />  {/* alt="" because title follows */}
    <h3 id={`recipe-${id}-title`}>
      <a href={`/recipes/${id}`} className="after:absolute after:inset-0">
        {recipe.name}
      </a>
    </h3>
    {/* rating, time, kcal — non-interactive text */}
    <div className="relative z-10 flex gap-2">
      <button>Upravit</button>
      <button>Smazat</button>
    </div>
  </article>
  ```
  The `::after` pseudo-element makes the whole card clickable while keeping only ONE interactive link. Nested action buttons sit above via `z-10`.
- *Effort:* M (one-time pattern + Storybook example).

**A-H-07 — `frontend/index.html` head — SC 1.4.4 Resize Text + SC 1.4.10 Reflow (Level AA)**
- *What:* `<meta name="viewport" content="width=device-width, initial-scale=1.0" />` is fine, but is missing `maximum-scale` is correctly absent (good — don't block pinch zoom). However, the Component Library §4.2 hard-codes container widths in `px` (`--container-sm: 640px;` etc.) and §4.3 declares px breakpoints. There is no commitment to support 400% zoom (1.4.4) or reflow to 320 CSS px wide (1.4.10).
- *Why:* If layouts use fixed `px` widths inside, content will horizontal-scroll at 400% zoom. Reflow requires content to be usable at 320 px wide without 2D scrolling (with documented exceptions for tables/maps).
- *Fix:* In Component Library, add: "All layout containers must use `max-width` (never `width`), and inner content must be in `rem` not `px`. Test every page at 320 px viewport AND at 1280 px @ 400% zoom (effective 320 px)." Add a Playwright test for each critical-flow page at both viewports.
- *Effort:* S (spec) + M (Playwright tests).

### MEDIUM (friction)

**A-M-01 — Component Library §2.4 Tabs — SC 2.1.1 Keyboard + ARIA APG Tabs pattern**
- *What:* "Swipe gesture on mobile" + "Keyboard navigation" + "Badge support" — no spec for arrow-key navigation, `aria-selected`, `role="tablist"/tab/tabpanel`, automatic vs manual activation.
- *Fix:* Mandate Radix Tabs (`@radix-ui/react-tabs` — note: NOT currently in `package.json`; add it). Document activation mode (recommend manual: arrow keys focus, Enter/Space activates — better for screen reader users who don't want a route change on every arrow press).
- *Effort:* S.

**A-M-02 — Component Library §2.6 Tables — SC 1.3.1 Info and Relationships**
- *What:* "Sortable Headers", "Responsive Behavior", "Row Actions" — no spec for `<caption>`, `scope="col"`, `aria-sort` on sortable columns, or what happens to `<th scope>` in the "horizontal scroll on mobile" / "collapsible rows for details" responsive variants.
- *Fix:* Provide a `<DataTable>` primitive that takes a `caption` prop (required), uses `<th scope="col">` / `<th scope="row">` for the sticky-first-column variant, sets `aria-sort="ascending|descending|none"` per column, and uses `<details>/<summary>` for the collapsible-row variant (native a11y).
- *Effort:* M.

**A-M-03 — Component Library §3.4 Recipe Rating Stars — SC 1.3.1 + 4.1.2 + 2.5.8**
- *What:* "Half-star precision … Click to rate" — but rating widgets are notoriously broken for AT. No mention of role, value-now, value-min/max, accessible step.
- *Fix:* Implement as `<input type="range" min="0" max="5" step="0.5">` styled as stars, OR as a `role="radiogroup"` with 5 radios + a "no rating" option, OR (best) use Radix Slider primitive (already installed) with custom appearance and `aria-valuetext="4 z 5 hvězd"`.
- *Effort:* S.

**A-M-04 — `Component Library §5.4 Motion and Animation` + `framer-motion` in `package.json` — SC 2.3.3 Animation from Interactions (Level AAA but trending to required) + SC 2.2.2 Pause, Stop, Hide (A)**
- *What:* Spec says "Respect prefers-reduced-motion" — good. But framer-motion does NOT do this automatically; each `motion.*` component must check `useReducedMotion()` or transitions must be wrapped in a `MotionConfig` with `reducedMotion="user"`.
- *Fix:* Add a root `<MotionConfig reducedMotion="user">` wrapper, AND ban raw `transition-*` Tailwind classes >300 ms in PR review. Provide a `motion-safe:` audit script.
- *Effort:* XS for the wrapper, S for the lint check.

**A-M-05 — `react-hot-toast` in `package.json` — SC 4.1.3 Status Messages (Level AA)**
- *What:* Toasts shown via `react-hot-toast` default to `role="status"` (polite) for success and `role="alert"` (assertive) for error. This is *correct* — but only if the project sticks to `toast.success()` / `toast.error()` and doesn't use `toast()` (plain), which defaults to polite for everything including critical errors.
- *Fix:* Wrap `react-hot-toast` with a project-specific helper that disallows the plain `toast()` call and forces a semantic variant. Document in Component Library.
- *Effort:* XS.

**A-M-06 — `react-day-picker` (date picker) — SC 1.3.5 Identify Input Purpose + SC 4.1.2 + cs-CZ locale**
- *What:* Trip date pickers (US §218) must support keyboard nav, screen-reader date announcement, and Czech locale (Po/Út/St/Čt/Pá/So/Ne, "leden 2026" etc.). `react-day-picker` supports this but requires explicit `locale={cs}` import from `date-fns/locale/cs` (date-fns is in `package.json`).
- *Fix:* In the Component Library §3 (add a new entry for DatePicker), specify: `locale={cs}`, `weekStartsOn={1}`, ARIA `aria-label` per day cell with full date in Czech, and a *paired* text input fallback (autoComplete="bday" / "off") for users who prefer typing dates.
- *Effort:* S.

**A-M-07 — Component Library §3.2 Participant Coefficient Slider — SC 1.4.1 Use of Color + 4.1.2**
- *What:* "Min: 10%, Max: 300%", "Touch-friendly handle ≥44×44 px", "Number input alternative" — good. But: no `aria-valuetext` spec (e.g., "Jan Novák, 75 procent, ekvivalent dítěte"), no announcement on preset button activation, no live region for the calculated effect text ("600 kcal × 75% = 450 kcal portion").
- *Fix:* Use Radix Slider (installed). Set `aria-valuetext` to a humanized string in Czech. Wrap the "calculated effect" text in `aria-live="polite"`. Each preset button must include the percentage in its accessible name ("Dítě, 70 procent").
- *Effort:* S.

**A-M-08 — Component Library §2.7 Shopping List — SC 1.3.1 Info and Relationships**
- *What:* Grouped by category ("Grains & Cereals", "Proteins"…) shown as a flat text outline with bullets. No specification of whether categories are `<h3>` group headers (giving screen readers navigation by heading) or just visual styling.
- *Fix:* Mandate `<section aria-labelledby="cat-grains">` per category with `<h3 id="cat-grains">Obiloviny a cereálie</h3>` and a nested `<ul role="list">` (note: `role="list"` is needed because Tailwind's `list-none` removes the implicit list role in Safari).
- *Effort:* XS.

### LOW (polish)

**A-L-01 — `frontend/index.html:6` — meta description in English ("Plan your meals, manage recipes, and organize trips with ease") for a Czech app.**
- *Fix:* Localize to Czech.
- *Effort:* XS.

**A-L-02 — No `<meta name="theme-color">` for the brand color.** Accessibility-adjacent (affects PWA install, status bar contrast on mobile). Spec also mentions dark mode (§5.5) — needs a paired `media="(prefers-color-scheme: dark)"` theme-color.
- *Fix:* Add `<meta name="theme-color" content="#2D5016" media="(prefers-color-scheme: light)">` and dark counterpart in `index.html`.
- *Effort:* XS.

**A-L-03 — Component Library §3.5 Progress — "Linear Progress 75% complete" missing `aria-valuetext` for screen-reader-friendly phrasing.** Most screen readers say "75 percent"; in Czech this could be "75 procent dokončeno".
- *Fix:* Specify `role="progressbar" aria-valuenow={pct} aria-valuemin={0} aria-valuemax={100} aria-valuetext="75 procent dokončeno"`.
- *Effort:* XS.

**A-L-04 — Component Library §2.4 Breadcrumbs — missing `aria-label="Drobečková navigace"` and `aria-current="page"` on last item.**
- *Effort:* XS.

**A-L-05 — `class-variance-authority` in `package.json`** — when implementing variants, take care that disabled-look variants don't *only* remove pointer-events without also setting `aria-disabled`/`disabled` (the visual disabled state without semantic disabled is a known cva pitfall).
- *Fix:* Code-review checklist item.
- *Effort:* XS.

## Form a11y audit (per critical flow)

Since no source exists, this section specifies the **contract** every form in each flow must meet. Use this as the PR acceptance checklist.

### Flow 1 — Register / Login (`US §187`)

| Field | Required attributes |
| --- | --- |
| **Email** | `<label for>` linked; `type="email"`; `autoComplete="email"` (login) / `"email"` (register); `inputMode="email"`; `aria-required="true"`; `aria-invalid` on error; `aria-describedby` → helper + error |
| **Password (login)** | `autoComplete="current-password"`; must NOT block paste; "show password" toggle is a `<button type="button" aria-pressed={visible} aria-label="Zobrazit heslo">` |
| **Password (register)** | `autoComplete="new-password"`; password requirements stated in `aria-describedby` text BEFORE the field; strength meter is `role="progressbar" aria-valuetext="Středně silné heslo"` |
| **Confirm password** | `autoComplete="new-password"`; mismatch error tied via `aria-describedby` |
| **CAPTCHA** | **MUST NOT** use cognitive function tests (math, image-puzzle, "select all traffic lights"). Use proof-of-work or device-attestation. — SC 3.3.8 |
| **Submit button** | Has explicit text label ("Přihlásit se", "Vytvořit účet"); on submit, focus moves to error summary (`role="alert"`) if errors, or to first invalid field |
| **Whole form** | `<form aria-labelledby="login-heading" noValidate>`; native validation disabled, RHF + zod via `@hookform/resolvers` (installed); errors announced once on submit, not per-keystroke |

### Flow 2 — Recipe creation (`US §202`)

Multi-section form: basics → ingredients (dynamic list) → instructions → nutrition (computed).

- **Section landmarks:** Wrap each step in `<fieldset>` with `<legend>` (visible) OR `<section aria-labelledby="section-h">`. Step nav must be `<ol role="list">` with `aria-current="step"` on active step.
- **Dynamic ingredient rows (add/remove):** Each "Remove ingredient" icon button needs `aria-label="Odebrat ingredienci {{name}}"` (NOT generic "Remove"). On add, focus moves to the new row's first field. On remove, focus moves to the previous row's first field (or to "Add" button if removing the last row).
- **Inline unit selector:** Radix Select with `aria-label="Jednotka pro {{ingredientName}}"`.
- **Instructions textarea:** `<textarea>` with `aria-describedby` pointing to char counter text. Char counter must use `aria-live="polite"` and only announce on 90%/100% thresholds (not every keystroke).
- **Nutrition widget (computed):** Wrap in `aria-live="polite" aria-atomic="false"` so screen readers announce updates when ingredients change. Confidence indicator (Component Library §3.11) must include text equivalent of color.

### Flow 3 — Trip planning + drag-drop (`US §218, §263`)

- **Trip basics form (name, dates, participants count):** Standard FormField contract.
- **Day cards drag-drop:**
  - `@hello-pangea/dnd` keyboard mode active by default (space to pick up, arrows to move, space to drop, esc to cancel).
  - Screen-reader announcements via library's built-in `announce` callback, **localized to Czech**: "Den 3 přesunut na pozici 1 z 7", etc.
  - **Single-pointer alternative (required for SC 2.5.7):** Each day card exposes a "Přesunout" menu button with options "Nahoru", "Dolů", "Na konkrétní pozici…" (combobox).
- **Meal assignment within day:** Same drag-drop rules. The "Add meal" button at the end of each day must have an accessible name including the day ("Přidat jídlo do dne 3").
- **Participant coefficient editor (US §263):** See A-M-07.

### Flow 4 — Shopping list (`US §276`)

- **Generated list display:** `<h2>` per category section, `<ul role="list">` for items, each item a `<li>` with `<input type="checkbox" id="…">` + `<label for>`. Checkbox state must persist via the store (zustand or similar — `store/` folder exists).
- **Bulk actions toolbar:** `<div role="toolbar" aria-label="Akce nákupního seznamu">` with grouped buttons (Generate PDF, Email).
- **Export modal:** Standard modal contract (A-H-03). Format radio group is `role="radiogroup" aria-labelledby`; included-sections checkboxes are individually labeled.

### Flow 5 — Marketplace (`US §302`)

- **Card grid:** See A-H-06 for card pattern.
- **Filters sidebar:** `<aside aria-labelledby="filters-h">`; each filter group is a `<fieldset>` with `<legend>`.
- **Search input:** `<form role="search">` with labeled `<input type="search">` and visible submit; recent searches as `<datalist>` or combobox (Radix not yet installed for combobox — add `@radix-ui/react-combobox` or use Headless UI Combobox).
- **Rating display (read-only):** See A-M-03. Read-only variant uses `role="img" aria-label="Hodnocení 4,2 z 5, 156 recenzí"` on the stars wrapper, with the stars themselves `aria-hidden="true"`.
- **"Share" action:** Confirm modal with focus management per A-H-03. The shareable URL field must have `<label>` + a "Copy" button with `aria-live="polite"` announcement on copy ("Odkaz zkopírován").

## Color & contrast notes

Computed for the tokens in `Documentation/jidelnicek_Component Library.md:8-90` against white (`#ffffff`) and dark-mode neutral-900 (`#111827`) backgrounds. AA thresholds: **4.5:1** for normal text, **3:1** for large text (≥18 pt / ≥14 pt bold) and non-text UI (icons, focus rings, borders).

| Token | Hex | On `#fff` | AA normal | AA large | AA non-text | Recommended use |
| --- | --- | --- | --- | --- | --- | --- |
| `primary-600` | `#2D5016` | 9.04 | PASS | PASS | PASS | Body text, primary buttons, focus rings |
| `primary-700` | `#254119` | 11.34 | PASS | PASS | PASS | Hover state |
| `primary-500` | `#567f2d` | 4.34 | FAIL | PASS | PASS | Large text only, icons, borders |
| `primary-400` | `#789a4f` | 3.05 | FAIL | FAIL | PASS | Non-text UI only (icons, borders) |

| `secondary-600` | `#7d5633` | 5.99 | PASS | PASS | PASS | Body text in secondary contexts |
| `secondary-500` | `#9f6e42` | 3.62 | FAIL | PASS | PASS | Large text, icons |
| `success-600` | `#1ba37a` | 3.36 | FAIL | PASS | PASS | Icons + paired text label |
| `success-700` | `#157d5e` | 4.92 | PASS | PASS | PASS | Success body text |
| `success-500` | `#22c997` | 2.13 | FAIL | FAIL | FAIL | Backgrounds only |
| `warning-600` | `#d97706` | 2.97 | FAIL | FAIL | **FAIL** | NOT safe even for borders |

| `error-500` | `#ef4444` | 3.76 | FAIL | PASS | PASS | Large text, icons |
| `error-400` | `#f87171` | 2.71 | FAIL | FAIL | FAIL | Decorative only |

| `neutral-600` | `#4b5563` | 7.56 | PASS | PASS | PASS | Secondary body text |
| `neutral-500` | `#6b7280` | 4.83 | PASS | PASS | PASS | Helper text |
| `neutral-400` | `#9ca3af` | 2.85 | FAIL | FAIL | FAIL | Decorative only — DO NOT use for placeholders that convey info |

### Recommended actions

1. Add a "Contrast Approval" matrix to the Component Library (this table is a starting point). Mark every token with its approved use; ban the others for that use via lint.
2. **Warning colors are particularly weak.** Move warning text to `warning-700` minimum (and add an undefined `warning-800` darker shade). Never use `warning-500` or `warning-600` for text on white.
3. **Focus ring color:** Component Library §2.1 says "2px solid primary color with 2px offset" — use `primary-600` (9.04:1 contrast) on white backgrounds and `primary-300`/`primary-400` on dark backgrounds. Verify against SC 2.4.11 Focus Not Obscured and SC 2.4.13 Focus Appearance (both new in 2.2 — note: 2.4.13 is AAA, but the AA version 2.4.11 still requires the focus indicator to not be entirely hidden).
4. **Dark mode (Component Library §5.5):** Audit every token a second time against the dark background — most "passing on white" tokens will *fail* on dark and need their inverse twin.
5. **Test placeholder text:** Native `::placeholder` styles default to `neutral-400` ish — make sure helper text uses `neutral-600` minimum and that placeholders never carry information that's not also in a `<label>` or `aria-describedby`.
